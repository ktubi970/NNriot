# Consolidating SQLite databases

The merge command combines a historical source with a newer operational database into a **separate staged output**. It never treats a merge report as permission to replace the configured database or delete an original file. Stop collectors, trainers, and the web app before publication. Use explicit paths so the result does not depend on a process's environment or import order.

```powershell
python -m scripts.merge_databases `
  --source path/to/older.db `
  --target path/to/current.db `
  --output path/to/staged.db `
  --report path/to/merge-report.json `
  --dry-run
```

Review the dry-run JSON printed to the terminal, then run the same command without `--dry-run` to create the staged database and report. Put the output on the same volume as the target when you intend to publish it. A local example of a target is `runs/training_data_23h_20260922_191434.db`; choose your own actual path. Use fresh output and report names for a rerun.

The target wins where keys conflict. Only validated `CLASSIC` matches from the old source enter the staged operational tables. Incoming participants, match facts, training features, and labels are reconstructed or validated; source trainer state (`trained_records`) is not transferred. Player identities and aliases are retained; player statistics are not stored, they are derived from `match_participants` on read. Excluded, corrupt, and conflicting old rows and their related data are retained in a local gzip JSONL archive recorded by the report. The archive is part of the retention set when removing the old SQLite file. No candidate model is promoted by the database merge.

Before publishing, check the report's accepted and archived totals, SQLite integrity and foreign-key results, representative player history, and the canonical match and training rows that were supposed to win conflicts. Confirm the staged database and archive are readable and the merge report names the intended source and target. Rebuild and verify the analytics mart against the staged source; it is derived data, separate from the operational database.

Publication is an explicit maintenance step: close every SQLite connection, checkpoint WAL content, retain a rollback copy of the current operational database, then switch `NNRIOT_DB_PATH` to the validated staged result or replace the configured file. Keep the SQLite main file and its `-wal` and `-shm` sidecars together until connections are closed and checkpointed. Point `NNRIOT_ANALYTICS_DB_PATH` at the rebuilt analytics mart. Smoke test the web app, history, training command, and analytics health with the configured paths.

Delete only the specifically obsolete source and derived analytics files after those checks pass and the gzip JSONL archive and report are retained. Include their matching SQLite sidecars once safely checkpointed. Keep unrelated databases in worktrees, scratch directories, and other runs out of the cleanup. The merge tool itself does not publish or delete any database.

## Current schema and version verification

The application schema is v17. Read `SELECT MAX(version) FROM schema_version`; `PRAGMA user_version` is not the application migration ledger and can remain 0. v12 introduced indexed match participants, v13 added `player_spatial_embeddings`, v14 migrated the crawl queue to PUUID/region records, and v15 added `encoder_id` to `player_spatial_embeddings` (NULL for rows written before the encoder weights were committed). v16 added `matches.ingested_at` and `matches.fetched_by_puuid`; they are deprecated since v17, NULL for rows written since then, and their values move to `match_facts` through the backfill and the merger. v17 reworked collection provenance:

- `match_facts`, one narrow row per match: `queue_id`, `game_start_at`, `game_end_at`, `game_version`, `platform`, and availability (`ingested_at`, UTC milliseconds of the first insert; `fetched_by_puuid`, the participant whose match list returned it). They live outside `matches` because a column added there sits after the multi-kilobyte `raw_json` and costs an overflow-page walk per read; the v16 columns are deprecated for that reason. The writers fill them for new matches only. Matches stored before v17 get a row from `python -m scripts.backfill_match_facts --db …`. That script reads every legacy payload once and carries the v16 availability when it is coherent with the match; otherwise availability stays NULL (unknown).
- `match_sightings`: every time a match list returned a match, by whom, when, and what was done with it (`stored`, `already_stored`, `discovery_only`, `rejected`, `missing`).
- `anchor_selections`: who was picked as a collection anchor, from which source and when, append-only, with a ladder snapshot for rank-based sources. Matches played before a participant's selection on rank are never stored (`MatchIngestor`). The migration records legacy anchors as `legacy_crawl_queue` (priority ≥ 5) and `legacy_players_last_saved`.
- `trained_records` holds the trainer's bookkeeping, moved out of `training_dataset`, which gains `feature_extractor` and loses the unused `llm_*` columns.
- Times are INTEGER UTC milliseconds (`crawl_queue.created_at`/`processed_at`, `players.updated_at`, which replaces `last_updated`). `players` no longer stores `avg_kda`, `avg_gold` or `total_matches`. `match_participants` gains `team_id`.

The v17 step rebuilds `players`, `training_dataset` and `crawl_queue` with foreign keys off, copying rows verbatim and keeping AUTOINCREMENT sequences; it runs in one transaction, like every step since then. `core/database.py` applies ordered migrations. The 9 October serving/evaluation work opened the source read-only and made no schema changes. Keep the staged merge, backup, validation and publication protocol above for future schema/data changes.

## Schema v17 merge contract

`scripts/merge_databases.py` accepts only schema v17 inputs on both sides and refuses anything else (`only schema version 17 is supported`). To merge an older database, migrate a **copy** first, for example `python -c "from core.database import init_db; init_db('path/to/copy.db')"`, and never migrate the original. A test pins the tool's `SCHEMA_VERSION` to `core.database.SCHEMA_VERSION`, so a future migration fails the suite until the merger gets an explicit policy for it.

- **Crawl queue:** target rows and their ids are kept unchanged. A source entry matches on PUUID, or on Riot ID plus region for legacy rows without a PUUID. Conflicting entries (different priority, processed state or region) keep the target's version and archive the source row as `canonical_queue_precedence`. New valid entries are inserted with fresh AUTOINCREMENT ids, so they come after target entries of equal priority, and the original row is archived as `regenerated_queue_id` when its id changes. Entries with a synthetic PUUID, an unknown region, a non-integer priority, a processed flag outside 0/1, or no PUUID and no Riot ID are archived as `invalid_queue_entry`.
- **Spatial embeddings:** source rows are never imported. They are derived data, and rows written before v15 have no recorded encoder (`encoder_id` NULL). Target embeddings are preserved, identical source rows are skipped, other source rows are archived as `derived_embedding_not_merged`, and orphans as `orphan_relationship`. Matches imported from the source therefore have no embeddings in the staged output. Recompute them on the staged database with the pinned encoder; `scripts/compute_spatial_embeddings.py` refuses to append next to legacy or foreign rows, so use `--recompute-all` when the target holds any.
- **Match facts (v17):** recomputed from the raw match for every imported match. Their availability (`ingested_at`, `fetched_by_puuid`) follows the match. For a match present in the target, the target's row wins and a differing source row is archived as `canonical_precedence`; a later ingestion time can only remove history rows under an availability filter, never leak one. When the target has no facts row for a match it shares with an identical source payload, the source's availability fills it. An imported match keeps the source's availability when it is coherent: `ingested_at` is a positive integer not earlier than `gameCreation`, and `fetched_by_puuid` is one of its ten participants. Otherwise the value becomes NULL (unknown) and the original row is archived as `normalized_metadata`. A source match without a facts row contributes the deprecated v16 columns of its `matches` row under the same rule; those columns are copied verbatim, like the rest of the row. The merge does not re-apply the rule that keeps matches played before an anchor's selection on rank out of the database; that rule applies at ingestion only.
- **Collection provenance (v17):** `anchor_selections` and `match_sightings` are append-only and unioned. Identical source rows are skipped. New anchor selections get fresh ids (`regenerated_anchor_id` when the id changes). Rows with an invalid PUUID, source, region, time, disposition or ladder snapshot are archived as `invalid_anchor_selection` or `invalid_sighting`. Sightings of matches that were never stored are kept.
- **Training rows (v17):** imported rows use `json_utils.extract_pre_match_features`, as the ingestor does, and record it in `feature_extractor`. Before v17 the merger stored `extract_match_features`, which includes each player's final KDA and gold; the migration labels such legacy rows `json_utils.extract_match_features`. Source `trained_records` are archived as `trainer_state_not_merged`. Identity rows created by the merge have `updated_at` NULL: they were never refreshed from Riot.
- **Preservation check:** the report compares the canonical queue by `id`, embeddings by `(match_id, puuid)`, anchor selections by `id` and sightings on all their columns, in addition to the existing tables.
